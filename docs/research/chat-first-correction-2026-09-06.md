## 用户要求

用户通过主控聊天提供大致主题，项目目录、服务器工作目录和数据已准备好。主控使用设计好的专职代理与工作流：

1. 搜集论文等资料，确定研究课题和初步实验方案。
2. 同期派刊会专员分析投稿去向，研究目标刊会的高引用文章、近期范例、写法与格式，建立可持续更新的刊会资料库。
3. 汇报课题与方案，获得人工确认。
4. 编排子代理执行科研实验、分析与证据整理。
5. 使用前期文献、刊会资料与本研究真实结果帮助模型写论文。
6. 独立审稿团队点评与返修；后续导入真实论文和真实审稿意见，用于校准审稿团队。

“学习资料写作”与“模型参数微调”需要明确区分；前者可以先行，后者保留真实训练与评测路径，不能将检索或提示词声称为已训练模型。

## ChatGPT 6 Pro 方案与本地落地

[原始方案会话](https://chatgpt.com/c/6a9d882b-9a40-83ea-ae2f-cba5295c4534)基于用户原话和本地代码概述生成；Pro 没有直接读取仓库。其核心建议是复用既有 ResearchCampaign、文档存储、工作流与用户确认，不再创建调度平台。

- M1：聊天创建研究；文献与刊会专员并行；资料有来源与阅读范围；用户确认具体方案；确认后实际调用现有子代理工具产出本地实验交接文件。保存后可恢复、重复确认幂等。
- M2：复用现有真实实验与结果复核链；接入证据写作、三个独立审稿角色和一轮返修预设。
- M3：先建立真实审稿案例契约，后续用获准数据校准和评测；参数训练必须有实际训练任务和评测，不能用提示词或检索冒充。

已落地 M1 的产品与调用链，以及 M2 的写作/审稿预设、M3 的版本案例存储和模型上下文过滤。没有新增数据库表或第二份运行队列。刊会和文献按稳定 key 存进既有不可变文档，跨本项目研究可检索；尚未预填真实期刊档案或训练模型。Pro 提到的 source-candidates.ts 经代码核对属于技能候选来源，不是文献库，因此扩展真实的 research-documents.ts。

## 关键实现

- `research-assistant.ts`：主控指令、项目上下文、四种工作流预设、确认版本与目录绑定有效性、重启待交接判断。
- `native-research-control.ts`：会话由服务端绑定，可以从空会话 prepare；API 模型和 CLI 使用同一作用域检查。CLI 若没有子代理能力必须说明，不能把预设返回说成已派发。
- `research-knowledge.ts` / `research-documents.ts`：文献、刊会、审稿案例、实验交接、稿件意见；引用与原文定位、未知引用数、会议届次、同论文分组与版本、来源损坏检查。
- `api/research-assistant.ts`：方案卡读取、实际公开文本获取、用户确认与交接。用户确认不授予远端执行签名；模型工具不暴露确认操作。
- `bounded-scheduler.ts`：复用现有调度入口恢复未派发的已确认准备任务。已记入会话的运行失败通过“继续研究”明确重试，不静默重投远程任务。
- `.oph/team.json` / `research-template.ts`：补充刊会专员、实验准备员、稿件审查员；已定制角色不覆盖。
- `ResearchAssistantCard.tsx`：聊天中查看方案与资料、确认或修改、继续研究。复杂执行面只在高级详情挂载。沿用现有 UI 色彩与字体；UI 技能检索没有匹配项，折叠层次由项目设计判断确定。
